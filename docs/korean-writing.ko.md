# 한국어 UX 라이팅과 타이포그래피

새 프로젝트를 시작할 때 대표 업무 하나를 고른다. 사용자가 누구인지, 무엇을 누르는지, 시스템이 어디까지 처리했는지를 한 줄씩 적는다. 이 세 줄로 랜딩의 설명, 앱의 버튼, 결과 안내를 각각 작성한다.

## 화면에서 쓸 말

- 랜딩 첫 문장은 사용자가 할 수 있는 일을 말한다. 역할이 다르면 문장을 나눈다. 예를 들어 “관리자는 계약을 등록해요. 담당자는 내 예상 정산액을 확인해요.”
- 일반 안내는 한 문장에 한 가지 뜻을 담아 해요체로 쓴다. 소리 내 읽었을 때 실제로 건넬 법한 말인지 확인한다. 승인된 약관과 계약 조항은 원문을 따른다.
- 버튼에는 다음 동작과 대상을 적는다. 다음 단계로 이동하면 ‘다음’, 초안을 기기에 보관하면 ‘초안 저장’, 외부에 보내면 ‘발송 요청’이다. 안내에서 버튼을 가리킬 때에는 화면에 보이는 이름을 그대로 쓴다.
- 오류에는 확인한 사실과 가능한 다음 행동을 적는다. 입력 오류는 고칠 필드 옆에 둔다. 결제나 초대의 응답을 잃었다면 원래 요청의 상태를 확인하는 흐름으로 안내한다. 원인을 모르는 상태에서 인터넷 연결이나 사용자 입력을 원인으로 단정하지 않는다.
- 권한·동의 안내에는 사용할 정보, 목적, 선택 결과를 밝힌다. 저장 위치와 공개 대상이 달라지는 동작은 버튼 이름에서도 구분한다.

| 상황 | 모호한 표현 | 화면에 쓸 수 있는 예 |
|---|---|---|
| 연락처를 어디에 저장할지 선택 | 저장 | 휴대폰 연락처에 저장 / 내 명함첩에 저장 |
| 초대 링크만 생성됨 | 초대 완료 | 초대 링크를 만들었어요. 링크를 복사해 전달해 주세요. |
| 발송 업체가 요청을 접수함 | 전달 완료 | 발송 요청을 접수했어요. 상대방이 받았는지는 아직 확인할 수 없어요. |
| 읽기 요청 실패, 재조회 버튼이 있음 | 오류 발생 | 문서를 불러오지 못했어요. ‘다시 확인’을 눌러 주세요. |
| 입금 전 예상 금액 | 지급액 | 예상 정산액 |

## 글자와 숫자

1. 브랜드에서 정한 DDS 제목·본문·레이블 스타일을 먼저 연결한다. 한글·라틴 문자·숫자·원화 기호의 실제 글리프와 대체 서체를 확인한다. 웹은 문서의 기본 언어와 폰트 로드 전후를, Android는 시스템 글자 배율과 앱의 큰 글씨 설정을 함께 확인한다. [DDS 기본 명세](design-system.ko.md) · [Android 타이포그래피](mobile-native.ko.md)
2. 제목은 짧게 쓰고 본문은 어절 단위로 읽히게 한다. 웹 본문에는 `word-break: keep-all`을 사용할 수 있다. 긴 상호명·이메일·URL이 화면 폭을 넘을 때에는 해당 영역에 `overflow-wrap: anywhere`를 적용한다. 고정 높이와 강제 줄바꿈은 작은 창과 확대 화면에서 다시 확인한다.
3. 숫자는 제품의 로케일 포매터로 표시한다. 예를 들어 원화는 ‘1,234,500원’, 비율은 ‘3.5%’로 쓴다. 값과 단위는 함께 읽히게 하고, 표에서 금액을 비교할 때는 오른쪽 정렬과 고정폭 숫자를 활용한다. 긴 금액은 열 배치나 상세 화면으로 전체 값을 제공한다. 예상·확정·실제 지급과 세금 포함 여부는 계산 근거에 맞게 표시한다.
4. 버튼과 상태는 색·위치만으로 설명하지 않는다. 보이는 이름과 접근성 이름을 맞추고, 아이콘 버튼에도 동작 이름을 붙인다. 이미지에만 있는 필수 정보에는 같은 의미의 텍스트를 제공한다.

## 출시 전 검수

랜딩, 인증, 업무 목록과 상세, 입력, 동의, 오류, 빈 화면, 알림을 따라 한 번씩 읽는다. 공통 화면과 플랫폼별 화면을 구분하고 같은 버튼이 각 플랫폼에서 실제로 같은 일을 하는지 확인한다. 좁은 휴대폰, 큰 글씨, 데스크톱 확대, 키보드와 화면 읽기 프로그램을 사용한다. 긴 상호명과 큰 금액은 합성 자료로 시험한다.

검토 기록은 **화면·플랫폼 | 기존 문구 | 반영 문구 | 동작 근거 | 검증 방법**으로 남긴다. 소스 검토, 렌더링 확인, 실기기 확인을 구분해 다음 프로젝트가 검증 범위를 알 수 있게 한다.
