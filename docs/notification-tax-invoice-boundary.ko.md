# 알림과 세금계산서의 확장 경계

이 문서는 후속 팝빌 연동의 설계 경계다. 현재 실제 구현은 SOLAPI 알림 어댑터이며, 팝빌 알림·세금계산서 발행 기능은 구현하거나 실행하지 않았다.

## 모듈과 식별자

| 경계 | 책임 | 독립 식별자 | 상태 의미 |
| --- | --- | --- | --- |
| 알림 공급자 | 문자/알림톡 한 요청의 접수 및 조회 | 앱 알림 intent UUID + 공급자 group/message reference | accepted는 공급자 접수; 수신 완료나 업무 완료가 아님 |
| 세금계산서 문서 처리 (향후) | 발행 요청, 원문/세무 결과 조회와 문서 상태 관리 | 회사별 문서 ID + 발행 명령 UUID + 공급자 문서 reference | issued/rejected/unknown은 문서 처리 결과 |
| 문서 발행 안내 (향후) | 이미 확인한 문서 결과를 당사자에게 전달 | 문서 ID를 참조하는 별도 알림 UUID | 안내 실패가 문서 발행 실패로 바뀌지 않음 |

`NotificationProvider.send()`에 세금계산서 원문·공급가액·발행 명령을 넣지 않는다. 팝빌 알림 어댑터가 생겨도 팝빌 문서 어댑터와 별도 모듈, 설정, 권한 검사 및 테스트로 다룬다. 회사별 사업자 인증과 문서 발행 권한을 단순 알림 발송 권한으로 대신하지 않는다.

## 향후 발행 상태와 멱등성

1. 서버가 발행 권한·회사 범위·문서 원문을 검증하고 문서 ID/원문 fingerprint/발행 명령 UUID를 고정한다.
2. 영속 발행 시도 기록과 CAS 경계를 확보한 뒤 한 번 요청한다. 공급자의 관리번호 중복 방지 계약은 실제 공식 API와 대조하여 별도로 검증한다.
3. 발행 결과가 불명이면 동일 문서·관리번호를 조회한다. 타임아웃만으로 새 관리번호를 만들어 재발행하지 않는다.
4. 발행이 확인된 경우 문서 원장 상태를 확정하고, 필요한 안내 intent를 별도 outbox로 기록한다. 알림 발송 실패나 불명이 이 발행 상태를 되돌리지 않는다.
5. 안내 재시도는 알림 intent/조회 규칙만 따른다. 발행 함수를 다시 호출하지 않는다. 역발행·취소·수정세금계산서는 각각 실제 세무 계약과 권한을 가진 후속 범위다.

알림과 문서 모두 계정·회사·환경별로 키와 reference를 격리한다. request UUID는 공급자의 멱등성 보장을 자동으로 만들지 않는다. 조회의 빈 목록은 미접수 확정이나 재전송 허가가 아니다.

## 현재 완료 판정에 포함하지 않는 것

- 팝빌 공급자 등록, SDK/운영 인증, 실제 알림 발송, 세금계산서 발행/국세청 전송.
- 발행 관리번호·문서 원장·세무 취소/수정 절차의 운영 구현.
- JN 회사 사용료 원장 확정을 은행 지급 완료 또는 세금계산서 발행 완료로 해석하는 동작.

후속 구현 시 실제 공급자 문서·테스트 환경·회사별 인증을 확인한 뒤 이 경계를 구체적인 별도 문서 패키지로 구현한다.
