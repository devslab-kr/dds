# DDS 공통 업무 화면 규격: Layout · LeftNav · TopNav

작성일: 2026-10-22
상태: 대화에서 확인한 의도를 반영한 설계 검토본. 구현·배포 완료 문서가 아니다.

## 목표

사용자는 매번 서비스 개발 뒤 간격·본문·제목 크기를 다시 줄이는 일을 반복하지 않으려 한다.
FM Dental 업무 화면 같은 상단 메뉴형과 DevsLab Admin 같은 왼쪽 메뉴형을 DDS에서 조립한다.
같은 역할의 영역과 글자는 같은 규격을 쓰며, 서비스마다 CSS를 복사하거나 임의 수치를 정하지 않는다.
React·Solid·Vue·Svelte에서 같은 이름과 같은 시각 규격을 제공한다. 코드는 짧고 이해하기 쉽게 유지한다.

## 선택한 구조

1. `Layout`: 왼쪽형(`navigationPosition="left"`)과 상단형(`navigationPosition="top"`)의 영역 배치, 본문 폭·여백·모바일 전환을 담당한다.
2. `LeftNav`: 그룹·항목·아이콘·활성 상태·접기/펼치기를 담당하는 독립 세로 메뉴다.
3. `TopNav`: 같은 메뉴 모델을 사용하되 가로 메뉴·하위 항목 펼치기·모바일 탐색을 담당한다.
4. `ConsoleShell`: 기존 사용법을 유지하는 편의 컴포넌트다. 내부에서는 공통 Layout과 LeftNav를 조립한다.
5. 페이지 제목과 섹션 등은 기존 DDS 구성 요소와 역할별 타이포 규격을 사용한다. 프레임워크마다 별도 CSS를 만들지 않는다.

별도 `dds-layout`·`dds-menu` npm 패키지는 만들지 않는다. 각 프레임워크의 DDS 패키지에서 Layout·LeftNav·TopNav를 제공한다.
하나의 거대한 메뉴에 방향별 조건문을 몰아넣거나, 외부 설정 DSL·플러그인 계층을 추가하지 않는다.
레이아웃, 메뉴, 서비스 권한·라우터의 책임을 분리한다.

## 공통 규격 제안

현재 DDS 토큰과 승인한 Admin 화면을 기준으로 다음 역할을 고정한다. 글자 확대 시 사용자 브라우저 설정을 존중한다.

| 역할 | 크기 / 줄 높이 | 굵기 |
|---|---|---|
| 페이지 제목 | title-1: 24 / 32px | 700 |
| 섹션 제목 | title-2: 20 / 28px | 600 |
| 하위 제목 | title-3: 17 / 24px | 600 |
| 업무 본문·메뉴·테이블 | body-2: 14 / 20px | 본문 400, 메뉴 500 |
| 읽기용 긴 설명 | body-1: 16 / 24px | 400 |
| 필드 라벨 | label: 13 / 16px | 500 |
| 보조 설명·메뉴 그룹 | caption: 12 / 16px | 설명 400, 그룹 600 |

글꼴은 현재 DDS sans 체계(Geist·Pretendard 및 시스템 대체 글꼴)를 사용한다. 글꼴 파일은 호스트의 기존 배포 방식을 재사용한다.
역할별 크기·줄 높이·굵기는 토큰으로 연결하고, 화면별 h1/h2/font-size 덮어쓰기를 공통 화면 개발 방식으로 사용하지 않는다.

| 영역 | 공통 기준 |
|---|---|
| 왼쪽 레일 | 너비 232px, 내부 여백 세로 20px / 가로 12px |
| 상단 업무 바 | 최소 높이 56px, 긴 이름·확대 시 높이 확장 허용 |
| 본문 외곽 여백 | 넓은 화면 32px, 모바일 16px |
| 본문 폭 | workspace 1100px / form 900px / settings 800px / full |
| 제목과 본문·주요 섹션 사이 | 32px |
| 패널 안쪽 | 24px, 모바일 16px |
| 필드 사이 | 16px |
| 메뉴 아이콘과 글자 사이 | 8px |
| 세부 간격 척도 | 4·8·12·16·24·32px |
| 메뉴 행 | 데스크톱 최소 40px, 모바일 조작 대상 최소 44px |
| 모바일 전환 | 기존 ConsoleShell 기준 56.25rem(기본 글꼴에서 900px) |

상태 칩은 내용에 맞는 너비를 사용하고 단계 번호 원형과 스타일을 공유하지 않는다.
표는 기존 DDS Table의 행 밀도·헤더·빈 상태를 사용한다. 컴포넌트마다 다른 행 높이를 임의로 정하지 않는다.
서비스는 브랜드 색상·로고·메뉴 데이터·본문을 전달한다. 사용자 테마, 글자 확대, 언어, 긴 메뉴명을 같은 공통 규칙으로 처리한다.

## 조립과 동작

Layout은 header/navigation/content/footer 슬롯을 제공한다. 왼쪽형은 필요할 때 브랜드·레일 하단 영역도 받는다.
JSX, Vue slot, Svelte snippet 등 각 프레임워크의 기본 조립 방식을 사용한다. 화면별 거대한 설정 객체를 요구하지 않는다.
LeftNav/TopNav는 Layout 없이도 사용할 수 있다. 라우팅과 권한 검증은 서비스가 맡는다.

메뉴는 안정적인 항목·그룹 ID를 사용한다. LeftNav는 그룹별 접기를 선택하며 여러 그룹을 동시에 열 수 있다.
기본은 활성 항목의 그룹 열기이며, 지정한 초기값(빈 배열 포함)과 외부 제어 상태를 존중한다.
기존 ConsoleShell의 접기 옵션 없는 nav 그룹은 계속 펼쳐진다. 세션 저장과 이동 시 활성 그룹 열기는 앱이 담당한다.
아이콘은 장식용이고 접근 가능한 이름은 라벨로 제공한다.
TopNav는 업무 탐색용 링크와 공개된 하위 탐색을 사용한다. FM의 기존 키보드 탐색·하위 메뉴 접근성을 기준으로 검증한다.
네이티브 disclosure를 쓰는 경우 일반 링크 탐색 의미를 유지하고 불완전한 role=menubar를 붙이지 않는다.
모바일 탐색의 열기·닫기, Escape, 포커스 복귀, 닫힌 항목의 키보드 접근 차단을 공통 컴포넌트가 책임진다.
SSR과 hydration에서 동일한 초기 상태와 충돌 없는 ID를 제공한다.

## 기존 서비스와 릴리스

기존 업무 기능, 계정·권한, FM workspace 유지·이동·로그아웃·실시간 연결을 DDS로 옮기지 않는다.
첫 단계는 DDS 공통 규격과 두 레이아웃/메뉴를 완성하고, 각 프레임워크의 같은 예시 화면으로 검증하는 것이다.
그 뒤 Admin과 FM에 각 유형을 적용하면서 화면별 레이아웃·타이포 덮어쓰기를 공통 규격으로 대체한다.
전 서비스가 패키지 발행 즉시 자동 변경되는 구조는 아니다. 소비 서비스가 새 버전을 채택하고 빌드·배포해야 반영된다.

React·Solid·Vue의 기존 API는 보존한다. Svelte는 새 최소 패키지로 이 공통 화면 구성 요소만 먼저 제공하며,
전체 DDS 컨트롤·테이블이 이미 구현되었다고 표시하지 않는다. 공통 CSS와 토큰을 재사용한다.
현재 준비한 0.28.0 작업은 미발행이다. 확정 버전은 최신 main과 npm 상태를 다시 확인하고 Changesets로 결정한다.
사용자가 승인한 재배포 범위에 따라 필수 CI·코드 리뷰·패키지 설치/SSR/브라우저 검증 후 머지·공개한다.

## 검증 기준

- 같은 메뉴·본문 예시를 두 레이아웃과 네 프레임워크에서 비교해 같은 규격인지 확인한다.
- 데스크톱·390px 모바일·키보드·확대·긴 한국어/영문·RTL·밝은/어두운 테마를 확인한다.
- 그룹 접기, 외부 제어, 활성 항목, TopNav 하위 링크, 모바일 닫기·포커스, SSR/hydration을 행동으로 검증한다.
- CSS 문자열·컴포넌트 내부 변수명 같은 구현 복사 테스트는 추가하지 않는다.
- tarball을 새 소비 프로젝트에 설치해 타입·공유 CSS·SSR·실제 브라우저 동작과 프레임워크 의존성 분리를 검증한다.
- 패키지 발행과 Admin/FM 운영 반영은 각각 근거와 버전을 기록한다.

## 현재 작업 상태

- PR #117은 최초 React 옵션 변경으로 만든 초안이며 공통 Layout 전체가 완성된 PR은 아니다. 머지·발행하지 않았다.
- React·Solid·Vue 메뉴 분리 작업은 진행 중 작업으로 보관한다. 좁은 메뉴 검증 결과를 전체 공통 레이아웃 완료 근거로 쓰지 않는다.
- Svelte 초기 패키지와 실패 테스트가 로컬에 준비됐으나 공통 Layout 설계 확정 전 구현·발행 완료로 취급하지 않는다.
